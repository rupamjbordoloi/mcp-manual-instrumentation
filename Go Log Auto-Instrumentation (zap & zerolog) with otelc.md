# Go Log Auto-Instrumentation (zap & zerolog) with otelc

Oct 23, 2026 · @Rupam

## Overview

Add one file, `otel.instrumentation.go`, import the Platform log modules in it, and build with `otelc`. Your existing zap or zerolog logs are then exported to the OTel Collector as OpenTelemetry log records, with `trace_id` and `span_id` attached. No logging code changes.

This page covers only the log setup. Installing `otelc`, Go prerequisites and general `otelc` usage are in the [OpenTelemetry compile-time docs](https://opentelemetry.io/docs/zero-code/go/compile-time/) and the MCP instrumentation page.

| Logger | Module to import | What you get |
| --- | --- | --- |
| `go.uber.org/zap` | `.../ps-otel/instrumentation/go.uber.org/zap` | Every zap entry is also exported over OTLP, at the logger's own level. Your normal zap output is unchanged. |
| `github.com/rs/zerolog` | `.../ps-otel/instrumentation/github.com/rs/zerolog` | Every zerolog event is also exported over OTLP. `trace_id` / `span_id` are added to your own JSON output too. |

## Step 1: Add otel.instrumentation.go

Create `otel.instrumentation.go` next to `main.go`, in the package you build:

```text
<application>
├── go.mod
├── go.sum
├── main.go
├── instrumentation.go
└── otel.instrumentation.go
```

Paste this in, keeping only the logger line(s) your app uses:

```go
// This file is automatically generated by otelc pin for tracking instrumentations.
// Additional instrumentation imports may be added manually.

//go:build tools

//go:generate go tool otelc pin --generate
package tools

import (
	// Platform log modules: keep the one(s) your app uses
	_ "github.hdfcbank.com/HDFCBANK/ps-otel/instrumentation/github.com/rs/zerolog"
	_ "github.hdfcbank.com/HDFCBANK/ps-otel/instrumentation/go.uber.org/zap"

	// OpenTelemetry SDK setup and active-span tracking (required)
	_ "go.opentelemetry.io/otelc/instrumentation/go.opentelemetry.io/otel"
	_ "go.opentelemetry.io/otelc/instrumentation/go.opentelemetry.io/otel/init"
	_ "go.opentelemetry.io/otelc/instrumentation/go.opentelemetry.io/otel/sdk/trace"
	_ "go.opentelemetry.io/otelc/instrumentation/go.opentelemetry.io/otel/trace"

	// zap only: adds trace_id/span_id to zap's own console/file output
	_ "go.opentelemetry.io/otelc/instrumentation/go.uber.org/zap"
)
```

Also add a second file, `instrumentation.go`, in the same `main` package:

```go
package main

import (
	_ "go.opentelemetry.io/otel/sdk/trace"
)
```

`otel.instrumentation.go` is behind the `tools` build tag, so its imports never reach the compiled binary. This blank import puts the OpenTelemetry trace SDK into the build so `otelc` can hook it. Without it, active spans aren't tracked and log records go out without `trace_id` / `span_id`.

Then pull the modules into `go.mod`:

```bash
go mod tidy
```

What each import does:

- **`ps-otel/.../zap` or `ps-otel/.../rs/zerolog`**: the Platform log module. It hooks the logger at compile time and exports each record over OTLP.
- **`otel/init`**: creates the global Tracer, Meter and Logger providers from `OTEL_*` env vars. Without it, nothing is exported.
- **`otel`, `otel/sdk/trace`, `otel/trace`**: track the active span per goroutine, so log records get the right `trace_id` / `span_id` even when you log without a `context`.
- **otelc `go.uber.org/zap`** (zap only): writes `trace_id` / `span_id` into zap's local output. Skip it if you only care about the exported records.

If you also use the MCP or HTTP instrumentation, add those imports to the same file. For a full example, see `demo/app/mcp/server/otel.instrumentation.go` in the ps-otel repo.

## Step 2: Point the app at the OTel Collector

Configuration is env vars only. The minimum is a service name and the Collector's OTLP endpoint:

| Variable | Example | Purpose |
| --- | --- | --- |
| `OTEL_SERVICE_NAME` | `orders-api` | `service.name` on every log record |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `http://otel-collector:4318` | Collector OTLP endpoint (4318 = HTTP, 4317 = gRPC) |
| `OTEL_EXPORTER_OTLP_PROTOCOL` | `http/protobuf` or `grpc` | Must match the port above |
| `OTEL_LOGS_EXPORTER` | `otlp` (default) | Set `console` to print records locally while debugging |
| `OTEL_GO_DISABLED_INSTRUMENTATIONS` | `logs/zap` or `logs/zerolog` | Turns off log export without a rebuild |

The Collector needs a `logs` pipeline with an `otlp` receiver:

```yaml
service:
  pipelines:
    logs:
      receivers: [otlp]
      processors: [batch]
      exporters: [<your log backend>]
```

## Step 3: Build with otelc and verify

Build with `otelc` in place of `go build`, then run the binary as usual:

```bash
otelc go build -o app .

OTEL_SERVICE_NAME=orders-api \
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318 \
./app
```

To verify:

1. Trigger any code path that logs.
2. Check the Collector (a `debug` exporter on the `logs` pipeline prints received records), or query your log backend for `service.name = orders-api`.
3. Records logged inside a request or span carry `trace_id` and `span_id`, so you can jump from a log line to its trace.

To test locally without a Collector, run with `OTEL_LOGS_EXPORTER=console`. Records are then printed to stdout.

## Notes

- **Plain `go build` = no export.** Instrumentation is only woven in by `otelc go build`. The `tools` build tag keeps `otel.instrumentation.go` out of normal builds.
- **Regenerating the file.** `go generate` (`otelc pin --generate`) can rewrite the file. Check that the `ps-otel` log imports are still there afterwards.
- **zerolog:** don't add `trace_id` / `span_id` fields yourself, or they appear twice. Only the default JSON encoding is supported; events are skipped if zerolog is built with the `binary_log` tag.
- **zap:** export follows each logger's own level, so records your logger filters out are not exported. Loggers that already use the `otelzap` core are left alone, so there are no duplicates.
- **No `trace_id` on a record** means it was logged outside any active span (for example at start-up). That is expected.
